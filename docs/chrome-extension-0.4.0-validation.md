# Chrome 확장 0.4.0 검증 기록

## 문제와 변경

0.3.0은 프로필에 표시된 글만 읽어 1/n·2/n 이후 상세 화면 안의 후속글을 놓쳤다. 사용자가 0.3.0 설치·작동과 이 누락을 확인했다. 0.4.0은 프로필에서 순번이 있는 첫 글을 발견하면 상세 화면을 열고, 같은 작성자의 1..n 본문을 저장한 뒤 프로필의 기준 게시물 위치로 돌아와 다른 글을 계속 탐색한다.

연속글마다 확보한 번호, 누락 번호, 충돌, 완료 여부를 JSON과 Markdown에 보존한다. 1..n의 본문이 모두 확인되어야 완료이며, 중간 글을 확인하지 못하면 해당 묶음을 미완료로 남기고 다른 글을 진행한다. 타인의 댓글은 이 묶음에 포함하지 않는다.

약 35회 화면 저장 뒤의 중단에 해당하는 코드 경로도 재현했다. 기존에는 상태 확인 ping이 한 번 실패하면 DB의 running을 false로 바꿔 이후 정상 화면 저장까지 거절했다. 일시적인 연결 오류에서는 실행 상태와 자료를 유지하며, 탭 복원·활성화 때 위치를 확인하고 제한된 횟수로 다시 연결한다. 사용자 중지·보안 중단·다른 페이지 이동은 자동으로 되살리지 않는다. 실제 사용자 환경에서 메모리 절약 기능이 최초 원인이었는지는 미확정이다.

숨겨진 탭은 진행을 기다리고 다시 표시되면 이어간다. 브라우저 전체 종료·닫힌 탭의 자동 재개는 보장하지 않는다. 처음 시작한 시각을 복구 때도 유지해 45분 상한이 초기화되지 않는다.

## 실제 Threads 페이지에서 확인한 범위

2026-09-19 Chrome의 표시 DOM을 관찰했다. 전문이나 로그인 자료는 저장소에 넣지 않았다.

- 사용자 제공 [12편 표본](https://www.threads.com/@jingammmm/post/DdVi5vwCdyh): 상세 화면에 동일 작성자의 1/12부터 12/12까지 12개 본문 컨테이너와 고유 게시물 주소가 있었다.
- 같은 계정의 [다른 12편 표본](https://www.threads.com/@jingammmm/post/DddwQYfCWOG): 프로필에는 1/12·2/12가 보이고, 첫 글의 시각 링크를 클릭한 상세 화면에서는 12개 모두 로딩됐다.
- 상세 첫 글의 본문 컨테이너는 목록 및 후속글과 달랐다. 이전 목록이 숨은 DOM으로 남는 경우도 있어 활성 영역만 선택하도록 수정했다.
- 실제 스크롤 요소는 높이가 긴 region 자체가 아니라 document.scrollingElement인 경우가 있었다. 높이와 overflow를 함께 확인한다.
- 0.3.0에서 실제 원문과 일치했던 7,835자 긴 첨부 처리는 유지했다. 자동 시험에서 캡션·첨부 분리를 다시 검증했다.

사용자 표본의 게시물 ID(1→12): `DdVi5vwCdyh`, `DdVi5xGicZo`, `DdVi5yACewb`, `DdVi5xRiUGW`, `DdVi5xoidKo`, `DdVi5xKCaGQ`, `DdVi5xRiX1w`, `DdVi5x6iSKH`, `DdVi5wwieGo`, `DdVi5wNCbn1`, `DdVi5wsCW0A`, `DdVi5wHCR_H`.

Chrome 연결 복구 후 수정된 reader와 같은 본문 판독 로직을 읽기 전용으로 실행했다. 두 표본 모두 1/12..12/12와 오류 없는 본문 12개를 얻었다. 별도로 읽은 단락 innerText에서 서비스 순번 표식과 그 구분용 공백·줄바꿈만 제외한 문자열과 24편 모두 일치했다. 사용자 표본의 편별 Unicode code point 수는 26, 356, 256, 369, 214, 292, 294, 249, 246, 263, 304, 270이었다. 다른 표본의 돌아가기 버튼을 실제로 눌러 계정 목록 URL과 첫 글 링크로 복귀함을 확인했다.

이 결과는 실제 DOM 판독 검증이다. 새 확장을 Chrome에 다시 로드한 뒤의 프로필→상세→복귀→다운로드 전체 실행은 아직 검증하지 못했다.

## 자동 검증과 리뷰

- `npm test`: 90개 통과, 실패·생략 0(코어 26개, 확장 64개).
- `npm run test:extension`: 64개 통과. 실행 JS/MJS 8개 구문 검사와 `git diff --check` 통과.
- jsdom 실제 reader·chain·content 결합 시험: 프로필의 첫 12편을 저장하고 복귀한 뒤 두 번째 묶음도 수집한다. 돌아왔을 때 레이아웃이 바뀌어도 기준 링크의 화면 위치를 복원한다.
- 합성 20편 중 7편 누락은 missing=[7]이며 완료로 표시하지 않는다. 20/20 전체 번호 검증, 타인 제외, 동일 번호 충돌도 시험한다.
- 저장 ACK 전 이동 금지, 저장 대기 중 사용자 이동, 복귀 중 보안 화면, 숨은 영역과 잘못된 상세 URL, 기존 긴 첨부 보존을 시험한다.
- DB v1→v2 upgrade에서 기존 카드·본문·실행 상태 보존, checkpoint·연속글 재개방, 일시 ping 실패, 폐기·동결 후 복원, 명시적 중지, 복구 횟수·시간 상한을 시험한다.
- 독립 리뷰에서 발견한 복귀 중 보안 검사 누락과 저장 대기 후 낡은 클릭 가능성을 재현 시험으로 고쳤다. 수정 후 추가 필수 수정 사항은 발견되지 않았다.

이 시험은 모의 DOM·IndexedDB·Chrome API에서 수행한다. 유료 수집기나 실서비스 반복 요청을 테스트에 포함하지 않는다.

## 업데이트와 한계

기존 설치 폴더 경로를 유지한 채 파일을 교체하고 Chrome 확장을 새로고침한다. 삭제·재설치나 다른 폴더 선택은 확장 ID와 기존 저장 공간을 분리할 수 있으므로 기존 사용자에게 요구하지 않는다. 권한은 기존 activeTab·scripting·storage 그대로다. 같은 출처에서 경로를 이동할 때 activeTab 접근이 유지되는 것은 [Chrome 공식 문서](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)를 기준으로 했다.

DB 이름은 `threads-text-archive-v2` 그대로이고 스키마 버전만 2로 올려 chains 저장소를 추가한다. 기존 글을 삭제하지 않는다. 단, v1 DB를 여는 이전 코드로 파일만 되돌리면 VersionError가 생길 수 있으므로 0.3.0 코드만 복구하는 롤백은 적절하지 않다. 문제 발생 시 중지·내보내기 후 스키마 2를 유지한 수정판을 적용한다.

Chrome 확장 관리 화면은 브라우저 도구 URL 정책이 차단해 사용자 새로고침이 필요하다. 0.4.0 설치 후 실제 12편과 다음 게시물의 연속 수집, 중지·재개, JSON/Markdown 다운로드를 확인해야 한다. 전체 과거 글·삭제된 글·미지원 구조의 완전 수집은 미검증이다.

기존 설치 폴더의 10개 파일이 수정 전 백업과 일치함을 확인한 뒤 0.4.0으로 갱신했다. 소스·새 ZIP 압축 해제본·기존 설치 폴더의 11개 파일 SHA-256이 모두 일치했다. ZIP SHA-256: `3184C23FFF4F246FDB8B2B2CB99618672AA227C0A5BE2FE97B967409CFC80CD1`. 파일 교체는 완료했으며 Chrome 새로고침은 별도 단계다.

브랜치 `codex/chrome-long-text-archive-2026-09-19` 및 기존 [초안 PR #2](https://github.com/optimin1109/threadcrawl/pull/2)를 갱신한다. 병합·스토어 등록·운영 배포는 하지 않는다.
