# 실제 Threads 지원 범위 조사 — 2026-09-09

결론: API로 공개 계정 조회가 불가능하다고 단정할 근거는 없다. Meta가 공개 프로필 게시물 조회를 문서화했다. 그러나 이번 요구 전체를 공식 API만으로 충족한다는 근거와 실제 응답 검증은 부족하다. 따라서 이 초안에는 OAuth/API 수집 구현이나 DOM 스크래핑을 넣지 않았다. 실제 계정을 완전히 백업할 수 없다.

## 확인한 공식 자료

- [Meta 공식 Threads API Postman 컬렉션](https://www.postman.com/meta/threads/documentation/dht3nzz/threads-api): OAuth를 사용하는 `GET /profile_posts?username=...&fields=...` 예시가 있다. 자체 사용자 게시물 조회에는 날짜·커서 파라미터 예시가 있다. 이 사실만으로 다른 공개 계정의 1~2년 전체 기록이나 무제한 페이지 접근을 보장하지 않는다.
- [Meta 공식 답글 조회 요청](https://www.postman.com/meta/threads/request/2oj5hld/get-a-list-of-all-a-user-s-replies): 공개 검색 결과에서 `is_reply`, `root_post`, `replied_to`, `quoted_post`, `reposted_post` 필드를 확인했다. 본문 페이지 직접 열기는 도구 오류로 실패했다. 부모/답글 관계 자체는 동시 작성 묶음의 증거가 아니다.
- [Meta 개발자 게시물 조회 문서](https://developers.facebook.com/docs/threads/retrieve-and-discover-posts/retrieve-posts), [답글 조회 문서](https://developers.facebook.com/docs/threads/retrieve-and-manage-replies/retrieve-replies): 직접 열기 시 도구의 Internal Error가 발생했다. 열람한 것처럼 인용하지 않는다. 실제 앱 권한·사용 조건·응답 계약 검증은 후속 과제다.
- [Meta 긴 텍스트 첨부 발표](https://about.fb.com/news/2025/09/attach-text-threads-posts-share-longer-perspectives/): 2025-09-04 발표, 2025-10-22 갱신. 최대 10,000자 첨부와 Threads 내 읽기를 설명한다. 작성 기능의 존재는 API 읽기 전문성의 보장이 아니다.
- [Meta Threads 소개 및 웹/비로그인 설명](https://about.fb.com/news/2023/07/introducing-threads-new-app-text-sharing/): 2023-08 웹 로그인 경험, 2023-12 EU의 프로필 없는 열람을 설명한다. 지역별 현재 동작이나 과거 목록 깊이에 관한 동일성 보장은 없다.

## 필수 조사 항목별 결론

1. **공식 API만으로 요구 범위 수집:** 공개 프로필 조회 엔드포인트 존재 확인. 모든 요구 충족 여부는 현재 기술적으로 확인 불가. OAuth 앱·권한을 사용한 실제 호출을 수행하지 않았다.
2. **가장 오래된 접근 가능 게시물까지 탐색:** 커서 개념은 문서에 있으나 브라우저 무한 스크롤의 종료 조건, 실제 과거 도달 범위, 잘린 목록과 진짜 끝의 구별은 미확인. 빈 페이지나 스크롤 변화 없음만으로 완료 판정하지 않는다.
3. **최초 작성 묶음과 나중 자기 답글 구분:** 동시 작성 관계 및 순번을 확정할 공식 읽기 데이터 근거를 확보하지 못했다. 답글 부모, 근접 시각, 본문의 `1/N` 문자열로 묶음을 추정하지 않는다. fixture의 evidence는 합성 증거이며 실제 Threads 필드가 아니다.
4. **리포스트 본문과 시점:** `reposted_post`라는 필드는 확인되지만 대상 계정 리포스트 행위 시점과 원문 작성 시점을 안정적으로 구별하는 계약은 미검증. 원문 날짜를 리포스트 날짜로 대체하지 않는다. 어댑터에서 시점 검증 없이 저장 요청하면 명시적 실패로 처리한다.
5. **인용에서 덧붙인 본문:** `is_quote_post`, `quoted_post` 등의 표현이 존재하지만 실제 표시/반환에서 덧붙인 텍스트 분리가 정확한지는 실서비스 검증 필요. 코어는 어댑터가 분리하여 전달한 own-text 한 개만 받는다.
6. **긴 텍스트 전문:** 사용자 기능 존재는 확인했다. Postman의 `text_attachment`는 작성 예시이므로 임의 계정의 전문 읽기 가능성으로 확대 해석하지 않는다. 펼치기·전문 종료·본문 중복 여부를 실검증해야 한다.
7. **비로그인과 직접 로그인 차이:** 공식 안내의 열람/상호작용 차이는 확인했으나 현재 동일 계정의 목록 깊이 비교는 수행하지 않았다. 첫 전용 Chrome은 빈 프로필이다. 로그인 여부와 상관없이 이 버전의 실제 자동 수집은 비활성이다.

## 실제 어댑터를 구현할 때의 경계

`src/sources.mjs`의 `ThreadsSource`는 실패를 명시하는 골격이다. `fetch(cursor, {signal})`에서 검증된 정규화 후보와 다음 위치, 목록 종료 및 접근 범위 증거만 코어에 전달한다. DOM 선택자·비공개 API·전체 글 수는 만들어 넣지 않았다.

다음 구현은 공식 앱 권한과 소유/공개 계정의 실제 응답 표본을 확보하여 API 지원 부분부터 연결한다. 부족한 부분에 한해 사용자가 보는 전용 Chrome 어댑터를 붙인다. 로그인 필요·CAPTCHA·보안 확인·접근 제한 감지는 즉시 자동 수집을 멈추고 구체적 코드를 보고해야 한다. 단순 제한 응답(`rate_limit`)과 실제 접근 제한(`access_restricted`)을 혼동하지 않는다. 현재 코어의 오류 코드 처리는 합성 소스로만 검증했다.

가짜 성공을 막기 위해 어댑터 계약의 `coverageKnown`과 `end`를 모두 요구한다. 검증 증거가 부족하면 `coverageKnown=false` 및 구체적 `issues`를 전달한다. 모든 발견 항목은 저장·미디어 제외·답글 제외·실패로 분류한다. 소스의 거짓 선언까지 코어가 증명할 수는 없으므로 실서비스 어댑터 승인 전에 증거 검토가 필요하다.

## 요구사항의 미결정 지점

- 날짜를 넘는 최초 묶음의 대표 날짜는 README도 실검증 후 결정하도록 했다. 초안은 확인된 묶음 시작 날짜를 임시 표시하되 반드시 불완전으로 보고하고 부분별 시각은 상태에 보존한다.
- Markdown 원문 링크/기호는 렌더링 결과에서 문자를 보존하도록 이스케이프한다. 따라서 Markdown 원시 파일에서 역슬래시나 HTML 엔티티가 보일 수 있다. 링크를 강제 하이퍼링크로 만들지 않는다. 원문 텍스트는 상태 파일에서 그대로 확인할 수 있다.
- 인증 데이터, HTML 전체, 미디어 URL, 원본 URL, 반응 수를 입력 계약에서 받지 않는다. 본문에 사용자가 직접 쓴 텍스트/주소와 수집 메타데이터는 어댑터가 구분해야 한다. 실제 DOM에서 구별되었음을 검증한 것은 아니다.
